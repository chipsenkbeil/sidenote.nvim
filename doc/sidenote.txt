1. INTRODUCTION                                         *sidenote-introduction*

sidenote.nvim annotates source code with notes stored *outside* the annotated
file. A note attaches to a whole file, a line, or a range, and survives the
code it points at being edited, moved, reformatted, or deleted.

Two uses, both intended: durable personal margin notes, and a work queue an AI
agent can read and act on.

Because a comment changes the code and a note does not, you can annotate a
vendored dependency, a file you have no business editing, or a function you are
still deciding about, and nothing you write ends up in a diff.

The cost of that is anchoring: a note has to find its code again after the code
moves. See |sidenote-anchoring|.

==============================================================================
2. REQUIREMENTS                                         *sidenote-requirements*

Neovim 0.10 or newer, developed and tested against 0.12. No dependencies.

Optional, and independently useful: >

    nvim-orgmode    org editing of notes, because the prose file ends in .org
    treesitter      symbol capture, and a structural resolution tier
    git or jj       provenance stamping, never used for resolution
<

3. GETTING STARTED                                   *sidenote-getting-started*

There is no setup() to call. Every configuration field has a default.

Map the |<Plug>| mappings you want: >vim

    nmap <Leader>na <Plug>(SidenoteAdd)
    xmap <Leader>na <Plug>(SidenoteAdd)
    nmap <Leader>nv <Plug>(SidenoteView)
    nmap <Leader>no <Plug>(SidenoteOpen)
    nmap <Leader>nb <Plug>(SidenoteBrowse)
    nmap <Leader>nB <Plug>(SidenoteBrowseProject)
<
Annotate a line, write your note, save. A sign appears in the gutter. Edit the
code around it, reformat it, move it down the file — the sign follows.

4. CONFIGURATION                                       *sidenote-configuration*

                                                                *vim.g.sidenote*
Configuration is `vim.g.sidenote`: a table, or a function returning one. A bad
value is reported through |vim.notify()| and |:checkhealth|, and the defaults
are used, so a typo degrades the plugin rather than disabling it.

Defaults: >lua

    vim.g.sidenote = {
        filetype = "txt",
        strategy = { "project", "global" },

        global_dir = vim.fn.stdpath("data") .. "/sidenote",
        project_dir = ".annotations",

        indicator = { style = "sign" },
        preview = { style = "float", max_lines = 20 },
        editor = { style = "split", position = "right", size = 60 },
    }
<
                                                    *sidenote-config-filetype*
filetype ~
    Extension and filetype of prose files. Set it to "org" or "md" to write
    notes in that format; the extension is the entire format decision.

                                                   *sidenote-config-indicator*
indicator.style ~
    How a buffer shows that an annotation exists.
    One of "sign", "virt_text", "highlight", "underline", "none".

                                                     *sidenote-config-preview*
preview.style ~
    Where a note appears when glanced at with |<Plug>(SidenoteView)|.
    One of "float", "virt_lines", "split", "none".

    "virt_lines" hangs the prose under the annotated line as virtual text, so
    you never leave the code. It renders as plain text.

preview.max_lines ~
    Most prose lines rendered in a preview.

                                                      *sidenote-config-editor*
editor.style ~
    Where a note opens for writing.
    One of "split", "float", "toggle", "current", "tab".

editor.position ~
    "left", "right", "top" or "bottom".

editor.size ~
    Columns for a vertical split, rows for a horizontal one.

These are three knobs rather than one because they are three questions: how you
know a note exists, how you glance at it, and where you write it. A cheap
transient float for previewing and a persistent right split for editing is a
normal combination that one setting cannot express.

5. STORAGE                                                   *sidenote-storage*

                                                    *sidenote-config-strategy*
`strategy` is a string, a function, or a list of them tried in order: >

    project     <root>/.annotations/      fails when no project root is found
    global      <global_dir>/<key>/       never fails
    function    whatever fun(path) returns  fails when it returns nil
<
Each entry is strict on its own terms. "project" errors rather than quietly
falling back, because silent fallback is exactly wrong when you meant to commit
your notes; write the fallback you want in the list instead.

The list is also the read order. Reads union every store in it, earlier entries
winning on conflict; writes go to the first that resolves. So
`{ "project", "global" }` means "write to the project store when there is one,
and always show me both".

                                                       *sidenote-project-root*
A project root is found by looking for, in order: `.annotations/` itself, then
`.git` / `.jj` / `.hg`, then `Cargo.toml` / `package.json` / `go.mod` /
`pyproject.toml` / `*.rockspec`.

The first of those is what makes `mkdir .annotations` enough to opt a plain
directory in, with no repo and no configuration.

                                                        *sidenote-sidecar-pair*
Each annotation is two files: >

    <id>.org             your prose, never machine-written except by your own
                         confirmed edit in the browser
    <id>.metadata.json   our record, rewritten freely
<
Every record carries its own project key and a project-relative path, so moving
a store from global to in-repo is a `mv` rather than data loss.

In-repo notes are committed by default. The plugin writes files and does nothing
else; if you want them ignored, that is your `.gitignore` to edit.

6. COMMANDS                                                 *sidenote-commands*

                                                                   *:Sidenote*
:Sidenote {subcommand} [args]

    add        Annotate the current line, or the range given
    browse     Editable listing of this file's annotations
    project    Editable listing of every annotation in the project
    refresh    Re-resolve and repaint the current buffer
    view       Preview the annotation under the cursor
    open       Open the annotation under the cursor for writing
    next       Jump to the next annotation and preview it
    prev       Jump to the previous annotation and preview it

`browse` and `project` accept filters, which combine: >vim

    :Sidenote browse  --kind=todo
    :Sidenote project --status=orphaned
    :Sidenote project --kind=todo --state=open
<
`project` also accepts a path; without one it uses the project containing the
current file.

8. THE BROWSER                                               *sidenote-browser*

An editable listing in the spirit of oil.nvim: >

    ▍ note  open      lua/lobby.lua:42-57    race in lobby join
    ▍ todo  open      lua/lobby.lua:88       refactor onto the new API
    ! note  wontfix   lua/lobby.lua          the old retry loop
<
Every column is yours to edit. The gutter carries anchor status, which is the
one thing the machine owns.

Each note is a real fold, so `za`, `zR`, `zM` and your own fold mappings all
work. Expanding one reveals its prose, indented, which you can edit in place.

                                                     *sidenote-browser-writing*
On `:w`: >

    edit any prose line, including the summary   rewrites that note
    change kind or state                         updates the record
    change the position in the location          re-scopes, re-anchored
    change the path in the location              moves it, re-anchored
    type a new line with no id                   creates a file-wide note
    delete a row                                 deletes the note
<
`dd` on a collapsed row deletes the whole note, prose and all — a vim operator
applies to an entire closed fold, so that comes free.

Nothing is applied until you confirm, and anything that loses information is
listed separately.

                                                    *sidenote-browser-mappings*
Inside a browser buffer only: >

    <CR>       open this note's prose for writing
    <Tab>      jump to the next column
    <S-Tab>    jump to the previous column
    -          widen to every annotation in the project
<
Fold verbs need no mapping: the folds are real.

A filtered-out row is absent, not hidden, so saving a filtered listing can never
touch an annotation it did not show you.

9. LUA API                                                       *sidenote-api*

                                                            *sidenote.add()*
require("sidenote").add({opts})
    Annotate the current buffer. `opts.scope` is "file", "lines" or "range";
    `opts.range` is {line_start, col_start, line_end, col_end}.

                                                        *sidenote.entries()*
require("sidenote").entries([{bufnr}])
    Every annotation targeting a buffer, resolved against its current text.

                                                      *sidenote.at_cursor()*
require("sidenote").at_cursor()
    The annotation under the cursor, or nil.

                                                         *sidenote.browse()*
require("sidenote").browse({opts})
    Open this file's listing. `opts.filter` narrows by `kind`, `state` or
    `status`.

                                                 *sidenote.browse_project()*
require("sidenote").browse_project({opts})
    Open the project listing. `opts.path` names any file inside it.

                                                        *sidenote.refresh()*
require("sidenote").refresh([{bufnr}])
    Re-resolve and repaint, returning how many marks were placed.

                                                           *sidenote.view()*
                                                           *sidenote.open()*
                                                           *sidenote.next()*
                                                           *sidenote.prev()*
The verbs behind the matching mappings. Each returns a boolean saying whether
there was anything to act on.

10. FOR AGENTS                                                *sidenote-agents*

The store is plain files, so `rg` over `*.metadata.json` and the prose files is
a supported interface. There is also a headless resolver: >

    nvim --headless -l cli/sidenote.lua export /path/to/project
    nvim --headless -l cli/sidenote.lua list /path/to/project
    nvim --headless -l cli/sidenote.lua list /path/to/project --status orphaned
<
`export` prints JSON on stdout. `list` prints one line per annotation: location,
status, kind, state, summary, tab separated.

                                                     *sidenote-export-gate*
An annotation whose code no longer exists is never given a line number.

"attached" and "drifted" export with a resolved position and a confidence to
weigh it by. "ambiguous", "orphaned" and "filegone" export with
`code_no_longer_exists: true`, no `line_start`, and their original `anchor_text`
— so an agent can see what the note was written against and search for it,
rather than be pointed at whatever happens to sit at that line now.

This is not caution for its own sake. A naive single-line fuzzy matcher measured
8% precision against ground truth on real repository history: 51 firings for 4
correct placements. A guess presented as a location sends an agent to edit code
that was never the subject of the note.

`code_no_longer_exists` is always present, so branching on it needs no nil
check. `line_start` is the field that disappears.

Agents read; humans write. Nothing in this interface creates or resolves an
annotation.

11. ANCHORING                                              *sidenote-anchoring*

A note records the bytes it was attached to, the lines above and below it, and
several hashes. Finding it again runs a ladder, first unique win taking it: >

    L0  the whole file is unchanged           placed at the stored lines
    L1  the bytes at those lines still match  attached
    L2  the text appears exactly once         attached
    L3  several matches, context decides      attached, or ambiguous
    L4  matches once ignoring whitespace      attached, reformatted
    L6  scored fuzzy match >= 0.80            drifted, with a confidence
        below 0.60, or nothing found          orphaned
        the file itself is gone               filegone
<
Two thresholds rather than one, because a low-confidence guess presented as
truth rates worse with users than an honest orphan.

The 0.80 and 0.60 thresholds are measured, not chosen. The repository's
`harness/` samples real repository history and grades placements against
`git blame --reverse`, with the results checked in.

                                                    *sidenote-never-deleted*
A note is never deleted by the plugin. Losing the anchor changes a note's
status, never its existence, and orphaning only ever adds fields. Deletion is
always something you asked for.
