Annotate source code with notes stored outside the annotated file. A note
attaches to a whole file, a line, or a range, and survives the code it points
at being edited, moved, reformatted, or deleted.

Two uses, both intended: durable personal margin notes, and a work queue an AI
agent can read and act on.

==============================================================================
1. Why notes live outside the file                              *sidenote-why*

A comment changes the code. A note does not. You can annotate a vendored
dependency, a file you have no business editing, or a function you are still
deciding about, and the file itself never changes.

The cost is anchoring: a note has to find its code again after the code moves.
See |sidenote-anchoring|.

==============================================================================
2. Requirements                                        *sidenote-requirements*

Neovim 0.11 or newer, for `vim.fs.relpath`. No dependencies.

Optional:

optional      buys
nvim-orgmode  org editing of prose, with `filetype = "org"`
git           the commit a note was captured at, never used for resolution
jj            the change id as well, in a repository colocated with git

4. Getting started                                  *sidenote-getting-started*

Map what you want, then annotate a line. The note opens beside it for you to
write and save, and a sign marks the line in the gutter. The sign follows the
code as you edit it, reformat it, or move it down the file.

This set avoids the common collisions (`]s` is spell, and `]a`, `]b`, `]q`,
`]d` are Neovim defaults):

>lua
    vim.keymap.set({ "n", "x" }, "<Leader>sa", "<Plug>(SidenoteAdd)")
    vim.keymap.set({ "n", "x" }, "<Leader>st", "<Plug>(SidenoteAddTodo)")
    vim.keymap.set("n", "<Leader>sA", "<Plug>(SidenoteAddFile)")
    vim.keymap.set("n", "<Leader>sv", "<Plug>(SidenoteView)")
    vim.keymap.set("n", "<Leader>so", "<Plug>(SidenoteOpen)")
    vim.keymap.set("n", "<Leader>sb", "<Plug>(SidenoteBrowse)")
    vim.keymap.set("n", "<Leader>sB", "<Plug>(SidenoteBrowseProject)")
    vim.keymap.set("n", "<Leader>sr", "<Plug>(SidenoteRefresh)")
    vim.keymap.set("n", "<Leader>sh", "<Plug>(SidenoteToggleHighlight)")
    vim.keymap.set("n", "<Leader>sf", "<Plug>(SidenoteFollow)")
    vim.keymap.set("n", "<Leader>sp", "<Plug>(SidenotePen)")
    vim.keymap.set("n", "<Leader>sm", "<Plug>(SidenoteMenu)")
    vim.keymap.set("n", "<Leader>sd", "<Plug>(SidenoteDelete)")
    vim.keymap.set("n", "<Leader>sl", "<Plug>(SidenoteLoclist)")
    vim.keymap.set("n", "<Leader>sL", "<Plug>(SidenoteLoclistProject)")
    vim.keymap.set("n", "<Leader>sq", "<Plug>(SidenoteQflist)")
    vim.keymap.set("n", "<Leader>sQ", "<Plug>(SidenoteQflistProject)")
    vim.keymap.set("n", "]n", "<Plug>(SidenoteNext)")
    vim.keymap.set("n", "[n", "<Plug>(SidenotePrev)")

5. Mappings                                                *sidenote-mappings*

No default mappings are installed.

mapping                            does
`<Plug>(SidenoteAdd)`              Annotate the current line or selection
`<Plug>(SidenoteAddFile)`          Annotate the whole file
`<Plug>(SidenoteAddTodo)`          File a todo on the current line or
                                   selection
`<Plug>(SidenoteBrowse)`           Open the editable listing of this file's
                                   annotations
`<Plug>(SidenoteBrowseProject)`    Open the editable listing of every
                                   annotation in the project
`<Plug>(SidenoteRefresh)`          Re-resolve and repaint annotations
`<Plug>(SidenoteToggleHighlight)`  Toggle range highlights in this buffer
`<Plug>(SidenoteFollow)`           Toggle the note editor following the cursor
`<Plug>(SidenotePen)`              Rotate the active pen for new notes
`<Plug>(SidenoteMenu)`             Open the menu for the note under the cursor
`<Plug>(SidenoteDelete)`           Delete the note under the cursor, after
                                   confirming
`<Plug>(SidenoteLoclist)`          This buffer's notes as the window's
                                   location list
`<Plug>(SidenoteLoclistProject)`   The project's notes as the window's
                                   location list
`<Plug>(SidenoteQflist)`           This buffer's notes as the quickfix list
`<Plug>(SidenoteQflistProject)`    The project's notes as the quickfix list
`<Plug>(SidenoteCycleKind)`        Flip the note under the cursor between note
                                   and todo
`<Plug>(SidenoteCycleState)`       Cycle the state of the note under the
                                   cursor
`<Plug>(SidenoteCycleStateBack)`   Cycle the state of the note under the
                                   cursor, backward
`<Plug>(SidenoteCyclePen)`         Cycle the pen of the note under the cursor
`<Plug>(SidenoteCyclePenBack)`     Cycle the pen of the note under the cursor,
                                   backward
`<Plug>(SidenoteView)`             Preview the annotation under the cursor
`<Plug>(SidenoteOpen)`             Open the annotation under the cursor for
                                   writing
`<Plug>(SidenoteNext)`             Jump to the next annotation
`<Plug>(SidenotePrev)`             Jump to the previous annotation
`<Plug>(SidenoteViewNext)`         Jump to the next annotation and preview it
`<Plug>(SidenoteViewPrev)`         Jump to the previous annotation and preview
                                   it

Inside a browser buffer only:

mapping         does
`<CR>`          open this note's prose for writing
`gf`            jump to the code the note is about
`a`             create a note on a file, and open it
`t` `T`         cycle state forward and back, or kind or pen on their columns
`fk` `fs` `fa`  filter by kind, state, or anchor status
`ff`            filter by path substring
`fc`            clear every filter
`<Tab>`         toggle this note's prose, org-style
`<S-Tab>`       toggle every note: the index, or all the prose
`-`             widen to every annotation in the project
`g?`            this table, as a float

Fold commands need no mapping. The folds are real.

6. Commands                                                *sidenote-commands*

                                                                   *:Sidenote*
>vim
    :Sidenote add | browse | project | refresh | view | open | next
              | prev | highlight | follow | pen | loclist | qflist
              | show
<

`browse` lists this file's notes. `project` lists the whole project's, from
the project holding the current file or from a path you give it.

`add` annotates the current line, or the range the command was given. `add
scope=file` annotates the whole file, and `add kind=todo` files a todo instead
of a note. The two combine.

`loclist` fills the window's location list with this buffer's notes, and
`qflist` fills the quickfix list with the whole project's. `scope=file` or
`scope=project` overrides either default, and the four list mappings cover
both lists at both scopes. `:Sidenote qflist kind=todo state=open` is a work
queue you walk with `:cnext`.

Inside a list titled `sidenote`, a winbar names the verbs its keys gain. `t`
and `T` cycle a field exactly as in the browser: the word under the cursor
inside the `[kind state pen]` bracket decides which one turns, and anywhere
else on the line means state. `o` opens the prose, `d` deletes after a
confirmation that quotes the prose, `s` flips between this buffer's notes and
the project's, and `fk`, `fs`, `fa`, `ff` and `fc` filter as in the browser.
`g?` lists the verbs. Each change redraws the list in place with the cursor
held, so cycling a pen is pressing `t` on its word until the color is right.

The verbs are bound only while the list is sidenote's own, and a quickfix list
another tool filled keeps every key that tool mapped. Each item carries its
identity in `user_data`, for any other list-driven tool to read.

`show` narrows what every buffer paints. `:Sidenote show kind=todo` leaves
only the todos' marks, `state=resolved` shows what is done, and a bare
`:Sidenote show` widens back out. Hidden notes are still tracked, saved and
listed, and `next` and `prev` skip them. `vim.g.sidenote_state.show` mirrors
the narrowing for your statusline.

`browse`, `project`, `loclist`, `qflist` and `show` take the same filters
(`kind`, `state`, `status`, `path`, `change`, `commit`), which complete,
validate and combine:

>vim
    :Sidenote browse  kind=todo
    :Sidenote project status=orphaned
    :Sidenote project kind=todo state=open
    :Sidenote project path=lua/net
<

7. Configuration                                      *sidenote-configuration*

                                                              *vim.g.sidenote*
>lua
    vim.g.sidenote = {
        -- Extension and filetype of prose files
        filetype = "txt",

        -- Stores to use, tried in order; also the read order
        strategy = { "project", "global" },
        global_dir = vim.fn.stdpath("data") .. "/sidenote",
        project_dir = ".sidenote",

        -- What marks a project root, replacing the built-in list
        -- markers = { ".git", ".jj", "WORKSPACE" },

        -- Where scans cache resolutions; never inside a store, which may be
        -- committed
        cache_dir = vim.fn.stdpath("cache") .. "/sidenote",

        -- Pen fresh notes pick up: a name, or { note = "…", todo = "…" }
        -- pen = "yellow",

        -- Pens a note can carry, each naming the highlight group its ink
        -- uses; custom entries merge over these
        pens = {
            yellow = "SidenotePenYellow",
            coral = "SidenotePenCoral",
            blue = "SidenotePenBlue",
            green = "SidenotePenGreen",
        },

        -- Style: sign | virt_text | highlight | underline | summary | none.
        -- The overlay: off | on (toggleable defaults) | always | never
        indicator = { style = "sign", highlight = "on" },

        -- Where a note appears when glanced at:
        -- float | virt_lines | split | none
        preview = { style = "float", max_lines = 20 },

        -- Where a note opens for writing:
        -- split | float | toggle | current | tab
        editor = { style = "split", position = "right", size = 60 },

        -- Where a listing opens: split | float | current | tab.
        -- No size means sized to the listing's rows
        browser = { style = "split", position = "bottom" },
    }
<

Four display settings answer four questions: `indicator` is how you know a
note exists, `preview` is how you glance at it, `editor` is where you write
it, and `browser` is where a listing opens. A transient preview float next to
a persistent editor split is a normal combination that one setting could not
express.

A preview names what it shows. The float carries the note's location, kind,
state and ink in its winbar, and the `virt_lines` style leads with the same
line. A note longer than `max_lines` is cut, with a marker saying how many
lines were held back.

With the `sign` style, a sign spans every line of a note, and where notes
overlap the worst anchor status wins the gutter. A healthy note signs `▍`,
and a healthy todo signs `☐`, checked to `☑` once it is no longer open. A
hurt anchor shows its status instead of its kind: `╎` drifted, `?`
ambiguous, `!` orphaned, `✗` filegone. A stripe (`▍`, `╎`) repeats down
the span, while a badge shows on the first line alone with a `│` tail below
it, so a three-line todo reads as one. A healthy note with no prose yet shows
a dimmed sign, which marks it as a deletion candidate.

The `summary` style puts the first line of prose at the end of the annotated
line, in the note's pen when it has one.

`indicator.highlight` adds ink over the annotated text itself (a range by its
exact columns), in the note's pen or else the `SidenoteMark*` group for its
anchor status. `:Sidenote highlight` toggles it per buffer, the way `:set
spell!` does. `on` and `off` set where the toggle starts, and `always` and
`never` pin it. A capture made while the toggle has highlights hidden shows
them again.

A `template` function seeds the buffer a new note opens into. `ctx` carries
`path`, `filetype`, `scope`, `line_start`, `line_end` and `text`. The seed is
an unsaved edit, and the prose file stays empty until you write the buffer:

>lua
    vim.g.sidenote = {
        template = function(ctx)
            return { "* TODO " .. ctx.path, "" }
        end,
    }
<

PENS                                                           *sidenote-pens*

A note can carry a pen, which colors its ink like a highlighter. Four come
seeded (`yellow`, `coral`, `blue` and `green`, background washes in the
`SidenotePen*` groups), and custom entries merge over them. A pen named by a
highlight group uses that group, which is yours to define:

>lua
    vim.g.sidenote = {
        pens = { pink = "MyPinkWash" },
    }
<

A pen given two shades instead gets a group the plugin owns and re-inks
whenever `background` changes, as it does for the seeded pens. A shade opening
with `#` is a color, and anything else names a highlight group to follow, so a
pen can track your theme. Naming a seeded pen this way retints it:

>lua
    vim.g.sidenote = {
        pens = {
            teal = { dark = "#1f4f4a", light = "#ccefe9" },
            themed = { dark = "DiffAdd", light = "DiffChange" },
        },
    }
<

In the browser, `t` and `T` on the pen column cycle through `-` (none) and
every configured pen, or you can type the name and `:w`. A penless note keeps
the status ink. Anchor health stays on the sign either way, so a drifted note
is visible whatever pen it carries.

New notes take the active pen. `:Sidenote pen` changes it for the session.
Bare, it offers `none` and every pen, and with a name (`:Sidenote pen coral`,
`:Sidenote pen none`) it sets that one. `<Plug>(SidenotePen)` rotates through
the same ring. A pen chosen either way wins over the config.

Until you choose one, the active pen is `pen` from your config, either one
name or split by kind:

>lua
    vim.g.sidenote = {
        pen = { note = "green", todo = "coral" },
    }
<

THE PEN IN YOUR STATUSLINE                               *sidenote-statusline*

Live state is mirrored into `vim.g.sidenote_state`, a table your statusline
can read without calling Lua. The plugin never writes `vim.g.sidenote`, so
`vim.g.sidenote.pen` is the pen a session starts with and
`vim.g.sidenote_state.pen` is the one it holds now:

>vim
    set statusline+=%{get(get(g:,'sidenote_state',{}),'pen','')}
<

For a chip drawn in the pen's own ink, use the component:

>lua
    vim.o.statusline = vim.o.statusline
        .. "%{%v:lua.require'sidenote'.statusline()%}"
<

THE NOTE EDITOR                                      *sidenote-context-header*

A note opens under a winbar that names it: location, kind, state, and a swatch
in the note's ink (the pen's wash, or a squiggle with the `underline` style),
then its age and the change it was written against while the bar has room.
Below the winbar is a quote of the annotated code as it reads now, each line
behind its source line number and a `│`, closed with a divider. An anchor
short of exact shows its status and confidence in the status color, with the
originally captured line on a `was:` row.

Editing the annotated code redraws the quote, and a change made in the browser
shows on return. A note buffer carries `b:sidenote` (its id, store root and
source buffer), so browsing from inside a note lists the annotated file's
notes. When the editor moves to another note, it saves the one it leaves.

FOLLOW                                                       *sidenote-follow*

`:Sidenote follow` keeps the note editor pointed at the note under your
cursor. Crossing into another annotation re-points the editor without focusing
it, and prose you edited is saved before it moves, so the store on disk stays
current for the CLI and for agents. Over unannotated code the editor keeps the
last note. Closing the editor turns following off.

CHANGING A NOTE WHERE YOU STAND                                *sidenote-menu*

`<Plug>(SidenoteMenu)` opens a small menu on the note under the cursor. It
lists every kind, state and pen the note could take with the current ones
marked, plus open, view and delete. Pick a row with `j`/`k` and `<CR>`, with
the key an action row names, or with the mouse. Picking a value writes it at
once and keeps the menu open, so kind, state and pen can all change in one
visit. Delete confirms first and quotes the prose it would destroy.

The cycle mappings change one field of the note under the cursor with a single
key: `<Plug>(SidenoteCycleKind)`, `<Plug>(SidenoteCycleState)` and
`<Plug>(SidenoteCyclePen)`, the last two with `…Back` variants.
`<Plug>(SidenoteDelete)` is the menu's delete on its own, with the same
confirmation.

WHERE NOTES ARE STORED                                      *sidenote-storage*

`strategy` is a store name, a function, or a list of them tried in order:

strategy    resolves to                    fails when
`project`   `<root>/.sidenote/`            no project root is found
`global`    `<global_dir>/<project-key>/`  never
a function  whatever `fun(path)` returns   it returns `nil`

Each entry is strict on its own terms. A lone `project` errors when there is
no project root instead of falling back, and the fallback you want is written
into the list, as the default `{ "project", "global" }` does. That keeps a
note you meant to commit from landing in the global store unnoticed.

The list is also the read order. Reads union every store in it, earlier
entries winning, and writes go to the first that resolves. The plugin writes
only files, so an in-repo store is committed unless you ignore it.

A project root is the nearest directory at or above the file holding any
marker: `.sidenote/`, `.git`, `.jj`, `.hg`, `Cargo.toml`, `package.json`,
`go.mod`, `pyproject.toml` or a `*.rockspec`. The list ranks nothing, so a
`.git` below your `.sidenote/` is the nearer root and takes the notes of the
files beneath it.

`markers` replaces that list. An entry is a name, a `*` glob, or a `fun(dir):
boolean` that decides a directory for itself. `.sidenote/` marks a root
whatever you configure, so `mkdir .sidenote` is enough with no repo and no
config. To add to the built-ins instead of replacing them, configure a
function. It receives a copy of them and returns the set you want:

>lua
    vim.g.sidenote = {
        markers = function(defaults)
            return vim.list_extend(defaults, { "WORKSPACE" })
        end,
    }
<

WHAT A NOTE IS ON DISK                                      *sidenote-sidecar*

A note is two files named by its ULID, the prose and the plugin's record.
`filetype` picks the prose file's extension, and that is the entire format
decision. The record is always JSON. Capture creates the prose file empty, and
after that the plugin writes it only when you edit prose in the browser and
confirm. Every record carries its project key and a project-relative path, so
moving a store from global to in-repo is a `mv`.

>
    01J9F3K2X7Q4V8M2ZC5T0BQWE8.txt             your prose
    01J9F3K2X7Q4V8M2ZC5T0BQWE8.metadata.json   the plugin's record
<

8. The browser                                              *sidenote-browser*

An editable listing, in the spirit of oil.nvim. Each note is a header line
(kind, state, pen and location) above its prose, and every note starts folded,
so a closed fold shows the summary. Anchor status is the one thing the machine
owns, and it lives in the gutter: nothing while a note is healthy, a status
glyph once it is not.

>
      note  open     yellow  lua/lobby.lua:42-57
      race in lobby join ⋯
      todo  open     -       lua/lobby.lua:88
      move onto the new API ⋯
    ! note  wontfix  -       lua/lobby.lua:120
      the old retry loop ⋯
<

The header is an ordinary line you can edit, move over and search. The prose
beneath it is one real fold, so `za`, `zR`, `zM` and your own fold mappings
work on it. Expanded, the prose sits verbatim at the margin with the summary
as its first line, editable in place and copyable exactly as stored.

The listing opens in a split below, sized to its rows.
`vim.g.sidenote.browser` picks another surface (`float`, `tab`, or `current`
to take over the window), with `position` and `size` when the default fits
badly. From a split or float, the keys that leave the listing (`gf`, `<CR>`,
`a`) land in the window you came from, the way a quickfix jump does. A split
stays open and a float closes behind you.

On `:w`:

edit                                   result
any prose line, including the summary  rewrites that note's prose
`kind`, `state` or the pen             updates the record
the position in the location           re-scopes it, re-anchored
the path in the location               moves it, re-anchored
deleting a note's lines                deletes the note

Deleting a note means deleting all its lines. An operator motion over a closed
fold takes the whole fold, so `dj` on a header takes the header and all its
prose. Deleting only the header cannot corrupt a neighbor: the prose left
behind would read as part of the note above, so the write is refused until
those lines go too.

Only `:w` applies anything. The listing is a projection of the store, so
closing an edited listing discards the edits and vim never asks you to save
it.

`-` widens to every annotation in the project, sorted by path then line. `a`
creates a file-wide note and opens it for writing, on the listed file or, in a
project listing, on a file you name (the row under the cursor is suggested).

Nothing applies until you confirm, and anything that loses information is
listed apart. Widening a note to the whole file drops its anchor:

>
    sidenote: apply 6 changes?

      WRITE    2 notes' prose
      CHANGE   kind   note -> todo
      MOVE     lua/lobby.lua:88 -> lua/net.lua:31   (re-anchored by content)

      ── these lose information ──
      RESCOPE  lua/lobby.lua:42-57 -> lua/lobby.lua   (DROPS ANCHOR)
      DELETE   "the old retry loop"   (REMOVES PROSE FILE)
<

FILTERING                                                 *sidenote-filtering*

Either listing narrows by `kind`, `state`, anchor `status`, or a `path`
substring. `change=` and `commit=` keep only notes whose version-control stamp
starts with the given prefix (see |sidenote-reviewing-a-change|). Filters
combine. Filtering a listing again narrows that listing in place, and `-`
carries the filter with it. Inside a listing the `f` keys ask interactively
(`fk`, `fs`, `fa`, `ff`) and `fc` clears them all. They refuse while the
listing holds edits you have not applied.

A filtered-out row is absent, not hidden, so saving a filtered listing cannot
touch an annotation it did not show you.

Cleanup is `:Sidenote project status=orphaned`, then `VGd` and `:w`.

9. Lua API                                                      *sidenote-api*

`sidenote.add({opts})`

Annotate the current buffer and open the new note for writing.

`sidenote.refresh({bufnr})`

Re-resolve and repaint a buffer's annotations.

`sidenote.entries({bufnr})`

Every annotation targeting a buffer, resolved against its current text.

`sidenote.at_cursor({entries})`

Annotation the cursor is in: the narrowest holding it, else a file-wide one.

`sidenote.browse({opts})`

Open the editable listing of this file's annotations.

`sidenote.browse_project({opts})`

Open the editable listing of every annotation in the project.

`sidenote.view()`

Glance at the annotation under the cursor without leaving the code.

`sidenote.open()`

Open the annotation under the cursor for writing.

`sidenote.next({opts})`

Jump to the next annotation; `view` also glances at it.

`sidenote.prev({opts})`

Jump to the previous annotation; `view` also glances at it.

`sidenote.toggle_highlight()`

Toggle this buffer's range highlights, the way spell is toggled.

`sidenote.loclist({opts})`

This buffer's annotations as the window's location list.

`sidenote.qflist({opts})`

The whole project's annotations as the quickfix list.

`sidenote.delete()`

Delete the annotation under the cursor, after confirming.

`sidenote.pen()`

The active pen's name, or nil when new notes start penless.

`sidenote.statusline()`

A statusline component: the active pen as a chip in its own ink, or "".

`sidenote.follow()`

Toggle the note editor following the cursor from note to note.

10. For agents                                               *sidenote-agents*

The store is plain files, so `rg` over `*.metadata.json` and the prose files
is a supported interface. Agents read everything. When an agent finishes a
todo it may write exactly two things: a dated response appended beneath your
prose, and the `state` field (`resolved`, or `wontfix` with the reason in the
response). Everything else stays human.

A ready-made agent skill at skills/sidenote/SKILL.md
<skills/sidenote/SKILL.md> covers how to read a store, which line numbers to
trust, and what an agent must never touch. Copy or symlink it into
`~/.claude/skills/` (or your agent's equivalent).

There is also a headless resolver, `cli/sidenote.lua` in the plugin's
directory. `export` prints the whole store as JSON on stdout. `list` prints
one tab-separated line per annotation (location, status, kind, state,
summary), narrowed by `--status`, `--change` or `--commit`:

>bash
    nvim --headless -l cli/sidenote.lua export /path/to/proj
    nvim --headless -l cli/sidenote.lua list /path/to/proj
    nvim --headless -l cli/sidenote.lua list /path/to/proj --status orphaned
<

REVIEWING A CHANGE                               *sidenote-reviewing-a-change*

An offline review is annotation plus a filter. Check out the change, read it,
and file todos where you would leave review comments. Every capture in a jj
repository colocated with git is stamped with the working copy's change id,
which survives the rewrites a commit id does not. An agent scopes itself with
`list <project> --change zzo`, does the work, appends a dated reply beneath
your prose, and flips each todo to resolved, so you review how each one was
addressed. In a committed store the comments travel with the working copy,
inside the change they review.

In a plain git repository the stamp is the commit sha, and `commit=` (or
`--commit` on the CLI) filters the same way. Use the sha you started the
review from as its key. Git has no id that survives an amend, so comments made
after you commit mid-review carry a different stamp.

One change's open comments, as a work queue:

>vim
    :Sidenote qflist change=zzo kind=todo state=open
<

WHAT AN EXPORT WITHHOLDS                                *sidenote-export-gate*

An annotation whose code no longer exists is never given a line number.
`attached` and `drifted` export with a position and a confidence. `ambiguous`,
`orphaned` and `filegone` export with `code_no_longer_exists: true`, no
`line_start` or `line_end`, and their original `anchor_text`, so an agent
searches for what the note was written against instead of editing whatever now
sits on those lines. A naive single-line fuzzy matcher measured 8% precision
against ground truth (51 placements, 4 of them correct).

`code_no_longer_exists` is always present, so branching on it needs no nil
check. The document holds `schema`, `project_key`, `generated` and the
`annotations` list, and a record carries `change` and `commit` when the note
was stamped. One record:

>json
    {
      "id": "01J9F3K2X7Q4V8M2ZC5T0BQWE8",
      "kind": "todo",
      "state": "open",
      "path": "lua/lobby.lua",
      "status": "attached",
      "confidence": 1,
      "code_no_longer_exists": false,
      "line_start": 42,
      "line_end": 42,
      "anchor_text": "function M.join_lobby(id)",
      "prose": "race in lobby join"
    }
<

11. Anchoring                                             *sidenote-anchoring*

A note records the bytes it was attached to, the lines around it, and several
hashes. Finding it again runs a ladder, and the first tier to place it
uniquely wins. A file-wide note is `attached` while its file exists.

tier                      test                       outcome
L0                        the whole file is          `attached`, at the stored
                          unchanged                  lines
L1                        the bytes at the stored    `attached`
                          lines still match
L2                        the text appears exactly   `attached`
                          once
L3                        it appears several times,  `attached`, or
                          and context decides        `ambiguous`
L4                        L2 and L3 again, ignoring  `attached`, or
                          whitespace                 `ambiguous`
L6                        a scored fuzzy match of    `drifted`, with a
                          0.80 or more               confidence
anything less, or         `orphaned`
nothing found
the file itself is gone   `filegone`

There is no L5. The number was reserved for a treesitter tier that was cut
before it was built.

A fuzzy match scoring at least 0.60 but under 0.80 is kept as a guess and
never placed, since a low-confidence guess presented as truth is worse than an
honest orphan. Both thresholds are measured. `harness/` samples real
repository history and grades placements against `git blame --reverse`, with
the results checked in.

Project-wide scans (the CLI, the project listing and project-wide lists) cache
their resolutions under `cache_dir`, keyed by the file content and the record
together. The cache never lives inside a store, and deleting it costs a rescan
and nothing else.

The statuses, in worsening order:

>
    attached | drifted | ambiguous | orphaned | filegone
<

WHILE YOU EDIT                                        *sidenote-live-tracking*

In an open buffer the ladder runs when the file is read and again after each
save. Between the two, the marks it placed track your edits directly: typing
inside a span grows it, deleting inside shrinks it, and edits above move it.
Saving writes that back, and the record re-baselines to the span the mark
tracked.

Two things never re-baseline. A mark placed on a guess (a drifted note) stays
a guess, so editing near it cannot turn the placement into truth. Typing over
or deleting a whole span collapses its mark and hands the decision back to the
ladder, which is what lets a line cut here be found again where you paste it.

NOTHING IS EVER AUTO-DELETED                          *sidenote-never-deleted*

Losing the anchor changes a note's status, never its existence. The status is
computed on every resolve and never written to the record. Deletion is always
something you asked for.

12. Limitations                                         *sidenote-limitations*

- Annotations live outside undo. `u` restores your code, never a deleted note.
The store is plain files, so commit it and your VCS can recover one. - A jj
repository with no colocated `.git` records no provenance, so its notes carry
no change id to filter on. - The browser's concealed ids need `:syntax on`.
Without it every row shows its raw ULID. - On macOS, `/tmp` and `/var` resolve
into `/private`. Stored paths use the resolved form, so outside tooling
comparing paths should realpath first.

13. Health                                                   *sidenote-health*

`:checkhealth sidenote` reports whether the configuration is valid, whether
the global store is writable, the project store at or above the working
directory, whether a capture there records provenance, and, when `filetype` is
`org`, whether nvim-orgmode is installed.
